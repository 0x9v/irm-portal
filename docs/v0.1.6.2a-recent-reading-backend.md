## Data model and migration

`document_reading_records` contains a UUID primary key, `user_id`, `document_id`, `last_page`, and timezone-aware `last_opened_at`. The row has a unique constraint on `(user_id, document_id)`, a database check requiring `last_page >= 1`, and cascading foreign keys to users and documents. The user listing index orders by `(user_id, last_opened_at DESC, id DESC)`; a document index supports document-side relationship operations. There are no copied document fields and no backfill. No separate `position_updated_at` was added; page writes update only `last_page` for existing rows.

Downgrading drops the new table and therefore discards reading records. The migration has not been run against an owner or production database.

## API contract

All routes require the current authenticated session and return personal responses with `Cache-Control: private, no-store`.

- `POST /api/v1/communities/{community_slug}/documents/{document_id}/reading/open`

  Example response: `{"last_page": 8}`. First open creates page 1. Later opens update `last_opened_at` and return the stored page without resetting it. Concurrent first opens use a database upsert against the unique key.

- `PUT /api/v1/communities/{community_slug}/documents/{document_id}/reading/position`

  Example request: `{"page": 8}`; response: `{"last_page": 8}`. The body permits only the integer `page`, range 1–100000. Booleans, floats, strings, extra fields, missing values, zero, negatives, and values above the bound receive the normal 422 validation response. The server does not parse the PDF or check its page count; the reader must clamp its restored page to the actual count.

  Concurrent writes are last-committed-write-wins. The future frontend should serialize or debounce page updates so an older in-flight page value cannot overwrite a newer one. If no row exists, the endpoint creates one with the current time; it does not invent an earlier open timestamp.

- `GET /api/v1/communities/{community_slug}/documents/recent?limit=20&after={record_uuid}`

  Example response:
  ```json
  {
    "items": [{
      "id": "document-uuid",
      "module_id": "module-uuid",
      "module_slug": "signals",
      "module_name": "Signals",
      "title": "Lecture notes",
      "type": "COURSE",
      "source": "OFFICIAL",
      "last_page": 8,
      "last_opened_at": "2026-10-11T12:00:00Z"
    }],
    "next_cursor": null
  }
  ```

  `limit` defaults to 20 and accepts 1–50. `after` is a UUID cursor scoped to this caller, community, and currently approved/readable documents. Malformed UUIDs receive 422; a valid cursor outside that visible set receives 404. SQL joins and filters by caller, community, and `APPROVED` before applying the limit; ordering is `(last_opened_at DESC, reading_record_id DESC)`. The response contains current module/document metadata only—no file paths, votes, or other users’ activity.

Unauthenticated requests receive the established 401. Unknown, foreign-community, pending, and rejected document IDs for mutations are concealed as 404. Reading state never grants file access. If an opened document later stops being approved, its reading row remains stored but disappears from the recent feed; existing file authorization remains authoritative.

## Handoff and boundaries

The frontend integration can call the open route only when the user deliberately enters the approved PDF reader, restore from `last_page`, serialize/debounce position writes, and consume the recent feed. It must clamp restored pages against the PDF’s actual page count. Ordinary page/card rendering, list/detail metadata requests, and downloads must not record opens.

No frontend files were edited. EtudSup, owner/development and production data, services, dependencies, deployment configuration, and Git staging were untouched. All changes remain unstaged and uncommitted.
