# ETUDSUP PR1 — post-reply image contract

Inspection and implementation plan only. PR1 adds no upload behavior. Announcement replies remain text-only and their endpoint, schema, composer, and removal flow stay unchanged.

## Current capability and evidence

- Post replies are JSON `{ "content": string }` at `POST /api/v1/communities/{community_slug}/posts/{post_id}/replies`. The response and paginated list contain `id`, `post_id`, `author_username`, `content`, and `created_at`. The schema trims content and requires 1–2,000 Unicode code points. The reply model has non-null text and no media or request identity. Sources: `backend/app/api/v1/endpoints/community_posts.py`, `backend/app/schemas/community_post.py`, `backend/app/models/community_post_reply.py`, `backend/app/services/community_post.py`, and migration `backend/alembic/versions/e7b1a2c3d4e5_create_community_posts_and_replies_tables.py`.
- An ACTIVE membership in the route's community is required to create/list/view posts and replies; the parent post is scoped to that community and must be visible. Creation locks the parent row, then commits one reply. Only an ACTIVE Delegate can remove a post or reply, including an author's own reply. Soft removal sets `removed_at`, keeps the original row/body, and hides replies when either the reply or parent is removed. Sources: `backend/app/api/deps.py`, `backend/app/services/content_removal.py`, `backend/app/models/content_removal.py`, `backend/app/api/content_route.py`, and `backend/tests/api/v1/test_content_removal.py`.

They keep the draft after ambiguous network/5xx responses and offer “Check Discussion”; pagination means that check cannot prove whether a particular late reply was created. The component already scopes reads to account/post changes and removes moderated rows. `frontend/src/app/communities/irm/posts/[postId]/page.tsx` mounts it by post/account. Existing cases are in `backend/tests/api/v1/test_community_posts.py`, `backend/tests/api/v1/test_community_posts_pg.py`, `backend/tests/services/test_content_removal_transactions.py`, `frontend/e2e/community-posts.spec.ts`, and `frontend/e2e/real-backend-posts.spec.ts`.
- Reusable safeguards exist in `backend/app/api/avatar_routes.py`, `backend/app/api/sticker_routes.py`, `backend/app/api/v1/endpoints/avatars.py`, `backend/app/api/v1/endpoints/stickers.py`, `backend/app/services/avatar.py`, `backend/app/services/sticker_library.py`, `backend/app/core/avatars.py`, `backend/app/core/stickers.py`, `backend/app/core/storage/base.py`, `backend/app/core/storage/exceptions.py`, and `backend/app/core/storage/local.py`: trusted Origin checks, bounded multipart streams and parts, Pillow decode/verify/load with EXIF transpose, worker-thread processing, immutable private files, bounded no-follow reads, and narrow cleanup after uncertain commits. ## Bounded first implementation

Allow **one static JPEG or PNG input file** with a post reply. Accept text-only, text plus image, and image-only (`content = ""`) replies. Do not add video, audio, GIF, external URLs, a crop editor, or background removal. Keep post creation and announcement replies as they are.

Announcement replies have separate text-only files: `backend/app/models/announcement_reply.py`, `backend/app/schemas/announcement.py`, `backend/app/api/v1/endpoints/announcements.py`, and `frontend/src/components/AnnouncementReplies.tsx`. PR2–PR4 must leave those paths' behavior intact.

### Creation and retry contract

Use **atomic multipart reply creation** on the existing `POST .../posts/{post_id}/replies` URL. A staged upload would need temporary asset ownership, expiration, attachment claims, and cleanup before a reply exists; one bounded multipart request fits the current parent-lock and single-reply transaction. Keep the existing JSON text-only request valid for older clients. New PR3 submissions, including text-only ones, use multipart and a client UUID; legacy JSON without that UUID retains its existing non-idempotent behavior.

Multipart fields are exactly `client_request_id` (required canonical UUIDv4, 36 ASCII bytes), `content` (optional UTF-8 text, at most 8 KiB raw and 0–2,000 code points after trimming), and `image` (optional, one file). Require nonempty trimmed content or an image. Parse with caps sufficient to detect an extra part (`max_files=2`, `max_fields=3`, `max_part_size=8 KiB`), then reject duplicate or unknown parts, extra files, non-string text fields, and caller-supplied author IDs, storage keys, or image URLs. Ignore the uploaded filename for storage. Require a single trusted browser `Origin` for multipart mutations using the existing configured-origin rule; keep the authenticated ACTIVE membership dependency. Validate the single `Content-Length` if present and count streamed bytes even when absent or inaccurate. Dispatch from `Request` after membership resolution so multipart parsing does not precede authentication.

For the new multipart flow, compute a SHA-256 request fingerprint from length-delimited trimmed text, normalized declared image MIME type, and the raw image-byte hash (or an explicit no-image marker). The browser keeps the same UUID, text, and `File` for retries. Scope uniqueness to `(post_id, author_id, client_request_id)`; check for a replay before and after taking the parent lock. A matching visible reply returns **200** and the same reply body; a first create returns **201**. A reused UUID with different payload, or one whose reply was removed, returns **409** and creates nothing. A database unique constraint backs up the lock. This follows the discussion-message retry behavior without using text matching or paginated reads as proof of creation.

First-create, replay, and list response items have the existing fields plus `image_url: string | null`; text-only replies return `null`. An image reply gets the relative URL `/api/v1/communities/{community_slug}/posts/{post_id}/replies/{reply_id}/image`, projected only from a validated server key. Return no storage key or arbitrary URL. All JSON success/error responses remain `Cache-Control: private, no-store`. Use the existing `{"detail": ...}` error envelope: 400 malformed multipart/header, 401 unauthenticated, 403 inactive membership or untrusted Origin, 404 missing/cross-community/removed parent, 409 request-ID conflict or removed prior reply, 413 body/file/canonical-output limit, 415 unsupported declared image MIME, 422 invalid fields or decoded image, and 500/503 storage or unresolved commit failure. Keep error detail short and free of decoder/path data.

### Image policy and limits

| Limit | PR2 contract |
| --- | --- |
| Multipart body | 5,308,416 bytes (5 MiB file plus 64 KiB fields/overhead), checked while streaming |
| Input file | Nonempty, at most 5,242,880 bytes (5 MiB) |
| Decoded image | Each side 32–4,096 pixels; at most 12,000,000 pixels |
| Canonical image | Longest side at most 1,600 pixels, no upscaling; JPEG quality 88, at most 2,097,152 bytes (2 MiB) |

Accept only declared `image/jpeg` or `image/png`, and require the decoded Pillow format to match. Reject multiple frames/animation, corrupt or truncated data, excessive pixels/dimensions, and decompression-bomb warnings/errors. Probe/`verify`, reopen/`load`, and apply EXIF orientation before sizing. Preserve the original aspect ratio with downscaling only; do not crop or add a square canvas. Composite PNG transparency over white and encode a fresh static RGB JPEG with no EXIF, ICC, comments, or source metadata. Reject output over the canonical byte cap. Run decode, resize, encode, and blocking storage/DB work off the async event loop. The client `accept` and size check are guidance; these server limits are authoritative.

### Authorization, persistence, and removal

Add nullable `image_storage_key`, `client_request_id`, and `request_fingerprint` to `community_post_replies` in one migration. The key is unique and server-generated; the last two are null for existing/legacy rows and jointly present for multipart rows. Add the scoped unique constraint above and a check that trimmed content is nonempty or the image key is present. Keep a single reply row, including for image-only replies. Do not add an asset table or change avatar, sticker, or document storage contracts.

Extend the filesystem storage abstraction with narrow post-reply methods. Use a canonical private key such as `post-replies/{reply_id}/{random_version}.jpg`, generated only by the server and validated against that reply ID. Publish immutably via temporary file, fsync, and no-replace link; reject symlink/path traversal on bounded reads and deletes. Never use generic public static serving or a caller-provided key.

Parse and fingerprint first, process the image outside the parent lock, then lock the visible parent and recheck the request ID. Generate a reply ID, save the canonical file, insert its key and fingerprint with the reply, and commit. On a known precommit rollback, delete only that generated key. If commit raises, resolve with a fresh session after serializing on the parent lock: a matching committed row means success/replay; proven absence permits deletion of that attempt's key. If the outcome cannot be established, retain the file, log its generated key for narrow follow-up, and return an uncertain server error. Never delete a file that might be referenced by a committed row. A retry with the same UUID resolves an uncertain client response without creating a second reply.

`GET .../posts/{post_id}/replies/{reply_id}/image` must require the same current ACTIVE membership as post/reply viewing, then join the requested community, visible parent post, and visible reply under that parent. An asset UUID or key alone never authorizes a read. Return 404 for wrong parent/community, removed post/reply, absent image, invalid key, or missing file; return 401/403 for the existing authentication/membership failures. A replay with a committed row but missing image bytes must report unavailability without creating another reply. Serve only bounded canonical JPEG bytes with `Content-Type: image/jpeg` and `Content-Disposition: inline`; apply `Cache-Control: private, no-store`, `Vary: Cookie`, and `X-Content-Type-Options: nosniff` to every media response, including errors.

Delegate removal remains the current soft removal with one audit event. A removed reply or parent immediately makes subsequent media GETs 404; parent removal need not rewrite child rows. Retain the private immutable file while its soft-removed row is retained, with no public route to it. PR2 deletes only a precisely known, unreferenced file from a failed creation attempt. Do not add an orphan sweep or broaden existing cleanup behavior. A later retention policy can address permanent deletion separately.

### Frontend contract

In `CommunityPostReplies`, add one JPEG/PNG picker, a local unsaved preview, replace/cancel controls, and visible **5 MiB** guidance. Keep the chosen file and text draft until 201 or matching 200 confirms creation. A synchronous ref lock plus disabled controls permits one in-flight submit. For an uncertain network/5xx outcome, keep the exact draft, file, and UUID, explain that posting is unconfirmed, and offer a safe retry with that UUID; do not generate a new request identity or claim success from a paginated “Check Discussion” read. A deliberate discard starts a new attempt with clear uncertainty wording. Keep status handling scoped to the current user, membership, community, and post.

Use `fetch(..., { credentials: "include", signal })` for the returned relative media URL, verify the response is JPEG, then display a blob URL. Abort on account/access/post/reply changes; revoke every server-image and unsaved-preview blob URL on replacement, cancellation, removal, logout, or unmount. Do not pass private media to the Next image optimizer or persist URLs. Render uncropped images with `max-width: 100%`, bounded height, `object-fit: contain`, and a screen-reader label such as “Image attached to reply by @author”; give the picker, preview, remove control, loading state, and failure state accessible names. Do not add this UI to `AnnouncementReplies`.
