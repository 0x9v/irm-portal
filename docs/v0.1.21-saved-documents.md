# Task 0.1.21 — Saved Documents

Implemented persistent, private saved-document relationships for the IRM community. The feature uses the existing approved-document access rule: a valid signed-in session is required, while ACTIVE membership is not. The approved module list and detail endpoints use the same authenticated-user gate.

## Existing access and data findings

- `Document` already stores its module, type, source, status, and creation timestamp. Its uploader and module are separate foreign-key relationships. Statuses include `PENDING`, `APPROVED`, and `REJECTED`.
- The module document list and approved detail are scoped to the requested community/module and include only `APPROVED` rows. Both require authentication but not ACTIVE membership. Pending/rejected document detail is concealed with 404. Upload and My Submissions have stricter ACTIVE-membership gates; Saved Documents follows the approved read gate rather than those upload/review gates.
- Documents belong to modules, and modules belong to communities. The saved row stores only user/document references and its save timestamp; document metadata is joined at read time.
- If a saved document becomes pending or rejected, its relationship remains stored, but it disappears from the saved feed and the saved-state/read endpoint will not grant access. If it is later approved again, it can reappear. A missing document is handled by existing document authorization.

## Storage and API contract

The new `saved_documents` table has UUID `id`, `user_id`, `document_id`, and timezone-aware `created_at` with a database `now()` default. It enforces unique `(user_id, document_id)`, cascades on actual user/document deletion, and indexes `(user_id, created_at DESC, id DESC)` plus `document_id`. No title, status, storage path, or file contents are copied into the relationship. No existing document, vote, or upload records are changed.

The endpoints are mounted with the existing `/api/v1/communities` router:

```http
PUT    /api/v1/communities/irm/documents/{document_id}/saved
GET    /api/v1/communities/irm/documents/{document_id}/saved
DELETE /api/v1/communities/irm/documents/{document_id}/saved
GET    /api/v1/communities/irm/documents/saved?limit=20&after={cursor}
```

PUT and DELETE return minimal state, for example `{"saved": true}` and `{"saved": false}`. The state GET returns the same shape. PUT performs an approved-document-scoped insert with database conflict handling, so repeat and concurrent requests do not create duplicate rows or leak uniqueness errors. Inaccessible/non-approved documents return the existing concealed 404. DELETE is idempotent and scopes its mutation to the caller and requested community, including when a previously saved document is no longer approved.

The list response is `{ "items": [...], "next_cursor": "..." }`. Each item has `id` (the approved document UUID), `module_id`, `module_slug`, `module_name`, `title`, `type`, `source`, `document_created_at`, and `saved_at`. The cursor is the saved-record UUID of the final returned row when another page exists. `limit` defaults to 20 and accepts 1–50. Results are filtered by current user, community, and `APPROVED` status in SQL before keyset pagination, sorted by `(created_at DESC, id DESC)`. A malformed UUID receives normal FastAPI 422 validation; a valid cursor outside the caller/community/visible set receives 404. Personal state and feed responses set `Cache-Control: private, no-store`.

## Frontend behavior

Authenticated users can save or remove approved documents from module cards or approved detail. The control loads its state from the API, disables duplicate clicks during requests, preserves the prior saved state on mutation failure, and offers retry. Guests do not see the control. Pending/rejected entries in My Submissions were not given save or reader actions.

`/communities/irm/documents/saved` shows title, module link, shared Task 0.1.20 type/source labels, saved date, approved detail link, and Remove action. It has distinct loading, request-error/retry, and genuine empty states, plus bounded Load more pagination. Page requests are aborted/generation-scoped; rendered private results are bound to the current user ID, and account/logout transitions clear prior rows. No saved identifiers are stored in browser storage.
