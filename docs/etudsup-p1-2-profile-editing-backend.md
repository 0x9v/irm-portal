# EtudSup P1.2 — own-account profile editing backend

## Scope and inspected contract

Implemented the narrow own-account mutation from [P1.1](etudsup-p1-1-profile-audit-contracts.md): `PATCH /api/v1/auth/me` updates only `username`, `first_name`, and `family_name`. The target UUID comes from the authenticated session's current `User`. The endpoint has no membership dependency, so an account with no memberships or a banned membership can still edit its account profile.

Before editing, the working tree contained extensive unrelated modified and untracked backend, frontend, migration, test, and documentation work. It was preserved. The files below identify this task's additions/deltas; several existing source files were already dirty and those pre-existing changes remain intact.

## API contract

| Method and path | Authentication | Request | Success |
| --- | --- | --- | --- |
| `PATCH /api/v1/auth/me` | Required valid database-backed session; target is session user | JSON object with only `username`, `first_name`, `family_name`; any supplied value must be a strict non-null string | `200` with current `UserResponse`: `id`, `username`, `email`, `first_name`, `family_name`, `created_at`, `updated_at` |

Example request:

```json
{"username":"sara_elm","first_name":"Sara","family_name":"El Mansouri"}
```

Example response:

```json
{
  "id":"11111111-1111-4111-8111-111111111111",
  "username":"sara_elm",
  "email":"sara@example.com",
  "first_name":"Sara",
  "family_name":"El Mansouri",
  "created_at":"2026-10-01T10:00:00Z",
  "updated_at":"2026-10-12T11:00:00Z"
}
```

Errors use the following stable forms (all responses generated by this route carry `Cache-Control: private, no-store`):

| Status | Example |
| --- | --- |
| 401 unauthenticated or invalid session | `{"detail":"Not authenticated"}` |
| 403 missing/null/untrusted Origin | `{"detail":"Untrusted request origin"}` |
| 409 exact username already exists | `{"detail":"Username is already taken."}` |
| 413 request exceeds 16 KiB | `{"detail":"Request body too large"}` |
| 415 non-JSON media type | `{"detail":"Content-Type must be application/json"}` |
| 422 invalid JSON shape, value, or extra field | `{"detail":[{"loc":["body","username"],"type":"string_too_short","msg":"Username must contain 3 to 50 characters"}]}` |
| 500 unexpected operation/commit failure | `{"detail":"Account operation failed"}` |

Validation errors expose only `loc`, `type`, and `msg`; input, validator context, raw body, SQL, and driver details are omitted. Unknown fields are forbidden, including email, password, avatar, caller user ID, role, permissions, administrator/account flags, and membership/application fields. Empty JSON object succeeds as a no-op. Omitted keys are never assigned. Explicit null, arrays, booleans, numbers, blank strings, and invalid lengths fail with 422. Non-object JSON fails with 422.

For a supplied value, raw text is checked for Unicode `Cc`, `Cs`, `Zl`, and `Zp` categories and bidi embedding/override/isolate characters U+202A–U+202E and U+2066–U+2069. Then Python `str.strip()` trims boundary whitespace. Username length is 3–50; names are 1–100 Unicode code points. Arabic and accented/combining Unicode remain supported. Case, internal whitespace, punctuation, and Unicode normalization form are preserved; no lowercasing, case folding, NFC/NFKC conversion, or transliteration is applied. Existing exact-string `uq_users_username` uniqueness remains authoritative. SQLite has an exact-column fallback for unit tests; PostgreSQL conflict mapping requires SQLSTATE 23505 and constraint `uq_users_username`.

If normalized supplied values equal the stored values, the service does not commit and `updated_at` does not move. A real patch assigns only the supplied changed User columns. The User UUID, email, password hash, creation time, sessions, membership rows, application fields, permissions, authored content, and uploader references are not changed. A commit or integrity failure rolls back the transaction; only the username constraint maps to the sanitized 409.

## Origin and request/error behavior

`AccountMutationRoute` is attached only to this PATCH route. Precedence is:

1. Require an exact trusted `Origin`; missing, `null`, malformed, lookalike, and untrusted values receive 403 before body processing or authentication.
2. Require `application/json` (charset parameters are accepted), else 415.
3. Reject a declared or streamed body over 16 KiB with 413.
4. Validate the session before FastAPI parses JSON or returns schema errors; guests with malformed JSON receive 401.
5. Parse/validate the strict schema; authenticated malformed or invalid bodies receive sanitized 422.
6. Resolve the current User dependency and apply the update.

The allowlist contains configured `frontend_url`; `localhost:3000` and `127.0.0.1:3000` are included only in development/dev/test. Origin matching compares scheme, host, and effective port exactly; WebSocket-only extra origins are not added. CORS remains separate and is not relied on for mutation authorization. No global route behavior was changed. The route performs a lightweight session preflight before FastAPI body validation to make the chosen auth/error precedence explicit; the normal current-user dependency then supplies the mutation target.

## Persistence and identity evidence

`update_user_profile` selects the session-derived User UUID with `populate_existing()` and `with_for_update()`, then assigns only normalized fields present in `model_dump(exclude_unset=True)`. PostgreSQL's row lock serializes same-account patches, so a request changing one field does not write a stale value over a concurrent omitted field. Different-user username races are arbitrated by `uq_users_username`; one succeeds and one receives 409 with its other changed fields rolled back. No availability pre-check is treated as authority.

The membership model stores submitted applicant identity separately from `User`. The API test captures both communities' application values, status, role, permissions, and timestamps before renaming and asserts they remain unchanged. Content and document ownership use the existing User UUID. Announcement, reply, post, and discussion `author_username` properties resolve the current related User on fresh reads; the test asserts fresh projection uses the new username while author/uploader UUIDs and literal content remain unchanged. Already-rendered client state and previously serialized messages are not rewritten or broadcast.

## Frontend handoff

Submit only fields the user actually changed, preserving omitted fields instead of sending empty values. Treat explicit empty edits as validation errors; do not send `null`. On 200, use the returned profile as the saved form baseline and refresh the shared account identity through the established auth refresh path. A refresh failure after a confirmed save should be reported separately from save failure. Never copy changed account first/family names into `Membership.applicant_first_name` or `Membership.applicant_family_name`; those remain submitted application snapshots. The response email is read-only and no avatar data is returned.

The existing `/auth/me` response shape is reused, so no response adapter or account ID lookup is needed. Preserve the session and current navigation state after successful edits. Fresh content reads pick up the current username through existing author projections; no identity broadcast was added.
