## Initialization and hydration

A static, parser-blocking inline script is in the root layout's head. It reads/validates storage in one guarded operation, then independently resolves System through a guarded `matchMedia`. Missing/unknown/JSON-like values select System; storage failure does not skip OS resolution. Missing/throwing matchMedia resolves System to light while explicit choices remain usable. The script writes only the root's two theme attributes and colour scheme; it embeds no dynamic user data and performs no persistence writes.

`suppressHydrationWarning` appears only on `<html>` because those two attributes and its colour-scheme style legitimately change before React hydrates. No descendant suppression is added. The provider uses stable System/light server markup for selectors through `getServerSnapshot`; that snapshot never writes root appearance. After subscribing, it uses browser state, preserving the bootstrap preference if a subsequent storage read fails. It never applies an interim SSR light theme to an initialized dark root.

The bootstrap and browser store intentionally contain small matching resolution paths; runtime tests exercise both together to guard against divergence.

No repository-defined CSP was found in the frontend source/config, deployment configuration or backend main header setup inspected. No CSP/security header or build configuration was changed. Live deployment headers were not fetched. If a deployment independently restricts inline scripts, authorize this exact static script with its hash or existing nonce mechanism; do not introduce broad unsafe-inline permissions.

## Lifecycle and selectors

- With no valid saved choice, follow System. Explicit Light/Dark ignore media changes; selecting System immediately resolves the live query.
- Updates change the current page even if storage writes fail. Such failed writes cannot persist a choice across reload; unavailable reads fall back to System, while bootstrap-to-hydration access changes retain the known bootstrap choice.
- One storage listener and one media listener are attached per provider store, including legacy media-listener support. Relevant cross-tab preference updates, corruption, key removal and localStorage clear events update state without writing back. Unrelated keys/sessionStorage are ignored. Listeners clean up on unsubscribe; unchanged choices do not write. The first subscription attaches listeners before re-reading storage to catch cross-tab changes made between rendering and attachment. Later React resubscriptions retain in-memory choices when persistence fails; a local interaction before first attachment also takes precedence.
- Desktop selector is in sidebar Region 3 above Logout; mobile selector is inside the existing drawer's Account section. Placement is unconditional, including guests, loading sessions and verification failures, so auth transitions do not gate or remount it.
- Each instance uses a native fieldset/“Appearance” legend, labeled Light/Dark/System radios and a unique `useId` group name. Native checked state exposes selection and native arrow keys support operation. Visible labels have minimum 44px height; text may wrap. Semantic backgrounds, borders, selected fills/text and a 2px focus outline with offset use the established palette. Visually hidden inputs remain keyboard/screen-reader controls.
- Both instances consume the same provider. The selector has no navigation, auth, form-submit or drawer-close handler. It introduces no icons, animation, dependency or floating UI.
