The right column stacks below the main content at smaller container widths. It has no calendar, progress indicators, fabricated module names, or notification counts.

Image 1 informed the left-sidebar shell and the dashboard’s main/supporting-column structure: hero, three-card row, announcements, then modules, with Quick Access and membership guidance beside them. Typography uses the existing local system stack (`ui-sans-serif`, system UI, Apple/Blink, Segoe UI, Roboto, Helvetica Neue, Arial). No package or remote font was added. The new hierarchy and styles are scoped to the Home dashboard classes; the existing shared font stack was not changed.

## Access behavior

- **No membership:** modules and Saved Documents remain available to signed-in accounts; the dashboard offers Request membership. Protected community shortcuts and announcement data are hidden.
- **PENDING:** shows application status and a link to the membership page. It makes no approval promise.
- **REJECTED / REMOVED:** explains the current state and links to the membership page, where the existing application flow permits reapplication.
- **BANNED:** hides reapplication and directs the user to Support.
- **ACTIVE member:** shows announcements, posts, discussion, pending documents, personal submissions, modules, and Saved Documents.
- **ACTIVE Moderator:** receives the active-member destinations and capability-gated Voting settings when `manage_document_voting` is true. No delegate-only management links are shown.
- **ACTIVE Delegate:** receives active-member destinations and the existing membership review, staff, and member-directory shortcuts. Voting settings still require the returned capability.
- **Membership verification error:** clearly says access could not be verified, hides protected destinations and announcements, and offers Retry Verification. Modules remain available to the signed-in account.
- **Membership refresh:** retains already-confirmed active content during a refresh; if membership is not yet known, shows a checking state and withholds protected content. No guest actions appear for a signed-in user.
- **Logout/account change:** module and announcement rows are associated with the current user ID, hidden during logout or account mismatch, and cleared on ineligibility. Requests are aborted and stale responses ignored.

Only the username is shown from account identity. Application identifiers, submitted names, promotion, and email are not rendered.

## Data requests and route decisions

The existing Home request contract is retained:

- Modules use `GET /api/v1/communities/irm/modules` for a signed-in account and display up to four returned modules with their actual names and `/communities/irm/modules/{slug}` routes. Loading, empty, error, retry, cancellation, and request-ID stale-response protection remain local to Home.
- Announcements use `GET /api/v1/communities/irm/announcements?limit=3` only after active membership is confirmed. The backend’s existing order is `created_at DESC, id DESC`. Each real row links to `/communities/irm/announcements/{id}`. Loading, empty, error, retry, cancellation, stale-response rejection, and clearing when eligibility is lost are preserved.
- The Saved Documents route exists at `/communities/irm/documents/saved` and is available to signed-in accounts. Membership, announcement, post, discussion, pending-document, and submission routes are shown only for active members. Delegate and voting-management destinations use the existing role/capability checks. Support is available at `/support`.
- Guest Home continues to avoid protected announcement and community requests as implemented in Task 0.1.22A.
