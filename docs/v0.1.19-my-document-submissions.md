## Existing lifecycle and access

`DocumentStatus` in `backend/app/models/document.py` has exactly three values:

- `PENDING` — student-source uploads awaiting community voting. Voting only accepts pending student documents. Once the saved threshold is met, more YES than NO votes changes the status to `APPROVED`; more NO than YES changes it to `REJECTED`; a tie remains `PENDING` (`backend/app/services/document_vote.py`).
- `APPROVED` — available through the ordinary authenticated module list, detail, reader, and module download routes.
- `REJECTED` — no longer available through module detail/download, inline view, global full-file download, or preview routes; those routes return 404 for rejected documents.

An active `MEMBER` upload is stored as `STUDENT` + `PENDING`. A `DELEGATE` can upload either `OFFICIAL` + `APPROVED` or `STUDENT` + `PENDING`. A `MODERATOR` can upload student documents as pending and can upload official approved documents only with the existing official-upload permission. There are no other document statuses or processing stages.

There was no suitable all-status “my uploads” endpoint. The existing pending-document list is community-wide and includes vote/access fields; it does not return approved/rejected uploads and is not appropriate for this private list. Existing `/api/v1/communities/{community_slug}/modules/{module_slug}/documents` remains approved-only, authenticated, newest-first and unchanged by this task. The new list uses the same active-community-membership gate as upload and the existing private pending-document list. This means an account without ACTIVE IRM membership cannot use it, even if it previously uploaded documents.

The module model already provides `id`, `slug`, and `name`; the list joins it in one query. The endpoint adds no count and follows the existing feed convention (`items`, `next_cursor`; `limit` 20 by default, 1–50; UUID `after` cursor). Module detail and module download require `APPROVED`. The global inline view requires `APPROVED`; global full download permits approved documents and pending student documents only for an active member with their own YES vote, which an uploader cannot cast. The preview endpoint allows authenticated users to preview pending or approved documents and returns 404 for rejected documents. Accordingly, the UI offers an approved reader link, a pending first-page preview link, and no file action for rejected documents. Every status includes a link back to its module.

The frontend gets the account from `AuthContext.user` and gates this page on `membership.status === "ACTIVE"`. It clears the request and private rows when the account or membership scope changes, aborts stale work, and only renders results associated with the current account and status filter.

## Endpoint contract

```http
GET /api/v1/communities/irm/documents/mine?limit=20&status=PENDING
Cookie: <authenticated session>
```

The caller must have an ACTIVE membership in the requested community. The SQL query restricts rows to both `Module.community_id == membership.community_id` and `Document.uploader_id == current_user.id`; module labels are joined, not fetched with N+1 queries. Optional `status` accepts only `PENDING`, `APPROVED`, or `REJECTED` and is applied before the cursor and limit.

Results are sorted by `(created_at DESC, id DESC)`. The cursor is the last returned document ID when another page exists. It is resolved only among this caller’s submissions in this community and under the active status filter. A valid cursor outside that scope returns 404; malformed UUIDs and unsupported status values return FastAPI’s normal 422 validation response. The endpoint fetches at most `limit + 1` rows to determine `next_cursor` and returns no total count.

Example response:

```json
{
  "items": [
    {
      "id": "5c05676b-7b0f-47dd-8d6b-41ca55075f08",
      "module_id": "e9262071-647a-448f-b9d0-5b3314640a19",
      "module_slug": "algebra-1",
      "module_name": "Algebra I",
      "title": "Exercise set 3",
      "type": "TD",
      "source": "STUDENT",
      "status": "PENDING",
      "created_at": "2026-10-01T10:30:00Z",
      "updated_at": "2026-10-01T10:30:00Z"
    }
  ],
  "next_cursor": null
}
```

The response includes only document/module identity, title, established type/source/status, and stored timestamps. It excludes uploader identity, storage and preview paths, votes, voter identities, and permission/review internals. Responses set `Cache-Control: private, no-store`.

## UI behavior

The page is at `/communities/irm/documents/mine`; active members can discover it beside Upload Document on a module page. It shows title, module, type, source, submitted date, and actual status. “All statuses” plus the three stored statuses are available. Empty unfiltered results say “You have not submitted any documents”; a filtered empty result says “No submissions match this filter.”

Pending explains that the student submission remains pending while community votes are collected and offers only the existing first-page preview route. Approved is described as available from its module and links to the existing reader. Rejected is labeled “Not approved,” says it is unavailable through the module reader, and has no file action or rejection reason. There is no review-time promise or invented review stage. Initial request errors offer Retry; next-page errors retain visible rows and retry the same cursor. Duplicate IDs are omitted when a page is appended.
