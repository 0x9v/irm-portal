## Product boundary and visibility decision

An avatar belongs to the **platform User UUID**, independent of IRM or any other membership. A signed-in owner may upload, replace or remove only their own image, even with no membership or a banned membership. No-avatar remains a valid state, with current username initials as fallback. These actions do not change account names/email, sessions, membership applications, permissions or authored-content ownership. No other-user edit, external URL import, administrator control or crop editor is part of the first implementation.

**Recommended initial visibility:** the owner's account response may include its avatar URL; any **authenticated** account may read a sanitized avatar image when it knows the exact current versioned URL. This permits a later avatar beside community content already authorized for that viewer, without making images anonymously/publicly accessible. It is deliberately broader than active membership in the author's community: even a signed-in nonmember who receives a URL can fetch the picture. The product UI should disclose that signed-in users can see the uploaded picture. Guests, expired/revoked sessions and anonymous `<img>` requests get 401. No avatar directory, user search or account JSON is exposed by image delivery.

Do **not** extend every announcement/post/reply/discussion schema during the first upload implementation. They currently render usernames, and their own authorization still controls content. A later, separate content-integration task can add a minimal nullable `avatar_url` to selected already-authorized author projections where the current author UUID is known. It must not serialize `UserResponse`, email, account names, memberships or application fields into content. Image delivery itself returns only canonical JPEG bytes. Existing author text and UUID references remain unchanged when an avatar changes.

## Proposed API contract

All paths are proposed under the existing `/api/v1` router. `avatar_url` is a **relative API URL**, not a storage key or arbitrary external URL. The server generates both UUID segments; the caller cannot choose the target User, filename, key or version.

| Method/path | Request/auth | Success | Errors and caching |
| --- | --- | --- | --- |
| `PUT /api/v1/auth/me/avatar` | Valid session, exactly one trusted `Origin`; `multipart/form-data` with required boundary and **exactly one** file part named `file`, no other parts/fields; part type JPEG or PNG. Owner comes solely from session. | 200 JSON `{"avatar_url":"/api/v1/users/11111111-1111-4111-8111-111111111111/avatar/22222222-2222-4222-8222-222222222222"}`. Newly versioned URL replaces the former one. | 400 malformed multipart; 401 unauthenticated; 403 Origin; 413 byte limits; 415 wrong request/unsupported input media; 422 missing/duplicate/extra part, MIME mismatch or invalid image; generic 500 unexpected processor/storage/DB failure. All `private, no-store`. |
| `DELETE /api/v1/auth/me/avatar` | Valid session and trusted `Origin`; **empty body**, no JSON/multipart requirement. Reject a nonempty body with private 400. | Idempotent 200 `{"avatar_url":null}`, including already absent avatar. A true no-op leaves `updated_at` unchanged. | 401/403 as above; generic 500 before commit; all `private, no-store`. Post-commit cleanup failure does not turn a confirmed removal into an error. |
| `GET /api/v1/users/{user_id}/avatar/{version}` | Valid session; no Origin requirement, membership gate or directory lookup. Parse both identifiers as UUIDs after authentication. | 200 **image/jpeg bytes** only; `Content-Type: image/jpeg`, `Content-Disposition: inline`, `Cache-Control: private, no-store`, `Vary: Cookie`, `X-Content-Type-Options: nosniff`. | 401 guest/revoked; same generic private 404 `{"detail":"Avatar not found"}` for malformed IDs, unknown User, no avatar, stale version or absent object; generic private 500 for unexpected storage failure. No paths/keys or private User fields in errors. |

On a future implementation, add nullable `avatar_url: string | null` to the **owner-only** `UserResponse` used by `/auth/me`, login and registration (new and legacy users get `null`). Existing fields remain. Upload/remove return only the small avatar state shown above, with no email, account names, membership details or storage key. Keep `PATCH /api/v1/auth/me`'s strict three-field allowlist unchanged; sending `avatar`, `avatar_url` or a caller User ID there remains 422. Avoid a second mutable avatar field in the profile PATCH schema.

The image URL changes on every successful replacement because the version is a fresh random UUID derived from the current stored key. Old-version GETs become 404 after pointer commit; removal yields null and 404. `private, no-store` prevents shared browser/proxy caches even for versioned URLs, while the version lets React/client image state abandon an old URL immediately. A request already in flight or an image already downloaded cannot be recalled.

### Multipart protection without weakening P1.3

Create a separate narrow avatar mutation route wrapper, sharing the **current** exact trusted-Origin predicate, duplicate-header/raw-syntax rejection, private error construction and session preflight. Do not broaden trusted origins or change global CORS. For PUT, require `multipart/form-data` with boundary; cap the **entire declared and streamed body at 2 MiB + 64 KiB** before Starlette/FastAPI multipart parsing, then inspect parser results for exactly one `UploadFile` named `file`. Also read that file at most 2 MiB + 1 byte. This bounds parser spooling and catches extra/duplicate parts even if a typed `File(...)` parameter would otherwise ignore them. For DELETE, require zero body bytes. Keep validation errors to `loc`, `type`, `msg` and never include filenames, raw bytes, parser context or image exceptions. Apply no-store to **success and every error**. Origin → media/body bounds → session preflight → multipart/schema parsing → normal dependency → mutation is the recommended precedence, matching the corrected account route's guest/malformed-body handling. The existing 16 KiB JSON wrapper must remain attached only to JSON profile/password routes.

For GET, use normal session authentication plus a small private image-response/error boundary; do not require Origin for a safe read. This needs explicit no-store on 401/404/500 too, because the ordinary `get_current_user` dependency alone does not add it. No `StaticFiles`, public directory, direct `FileResponse` from an unvalidated path, cross-origin image proxy without credentials, or API that accepts a storage key.

## Image limits and processing pipeline

| Step | Recommended first-release rule |
| --- | --- |
| Input bytes and formats | File bytes at most **2,097,152**; complete multipart body at most **2,162,688**. Accept JPEG (`image/jpeg`) and PNG (`image/png`) only. Declared part media type must match Pillow-detected `Image.format`; filename/extension are ignored. Empty and unsupported files fail. |
| Dimensions/decode | Before full pixel load, require width/height each **32–4096** and total pixels at most **16,000,000**. Treat Pillow `DecompressionBombWarning` as an error and catch its bomb/error, `UnidentifiedImageError`, truncated/corrupt data and decoder failures. `verify()` then reopen and fully `load()` the image under the same format/dimension checks. |
| Frames/active formats | Require exactly one frame. Reject APNG, animated PNG, GIF, WebP, AVIF, SVG/XML and every other format, even when a filename or MIME claims JPEG/PNG. Never pass active original bytes through to storage. |
| Orientation/color | Apply EXIF orientation in memory; recheck post-orientation bounds. Center-crop square, Lanczos-resize to **256×256**. Composite transparency onto a fresh opaque white RGB canvas; convert other supported decoded modes to fresh RGB pixels. |
| Canonical output | Encode **one JPEG**, quality **85**, with no EXIF, GPS, ICC, XMP, PNG text, comments, original filename or source bytes. Require resulting JPEG at most **262,144 bytes**; an oversize result is generic 422, while an unexpected encoder failure is generic 500. Do not keep multiple sizes or the original. |

Pillow already provides the needed decoder/encoder, so signature-only validation or a new processing dependency is unwarranted. Header format and dimensions must be inspected before expensive full decode; warning/error handling and the explicit pixel bound defend against compressed bombs. Encoding from a newly created RGB image, rather than saving the decoded object with its `info`, strips metadata. The implementation should run decode/encode in FastAPI's worker pool or equivalent bounded worker, not on the async event loop. Use synthetic image fixtures to verify actual output format, dimensions and absence of metadata; a matching Content-Type alone is never evidence of a safe image.

## Storage, database and crash consistency

**Minimum migration:** one nullable `users.avatar_storage_key VARCHAR(255)` column, default `NULL`. Existing accounts stay null; do not generate initials files or backfill pictures. An immutable internal reference has the strict server-generated form `avatars/<User UUID>/<version UUID>.jpg`. Validate that grammar and owner UUID before every read/delete, even for a database value. Keep the storage root writable only by the service; path resolution alone cannot defeat an attacker allowed to swap storage-directory symlinks concurrently. The URL is derived from the key, never persisted as an external address. No separate MIME, width, version or avatar timestamp column is needed for a fixed JPEG contract; the existing `User.updated_at` changes on a real pointer update. A true absent-avatar removal is a no-op. The Alembic upgrade adds the nullable column without rewriting existing rows. A downgrade with non-null references should refuse silent data loss until the owner explicitly exports/retires those images and clears references; only then drop the column. No migration is written here.

The first upload/replacement sequence should be: bound and validate/encode before a DB write transaction; lock and refresh the session-derived User row (`FOR UPDATE`); capture its current validated avatar key; generate a never-reused version key; save the new canonical bytes under that key; assign only `avatar_storage_key` and commit. The old pointer/file remains valid until the new save and DB commit succeed. If validation or file write fails, no DB pointer changes. If commit fails, roll back and delete **only the newly generated key**, recording any cleanup failure. After confirmed commit, delete only the captured superseded avatar-owned key; if cleanup fails, return the confirmed 200 and schedule/retry restricted cleanup. Do not call broad document deletion helpers. Use the same User row lock for removal: capture current key, commit null, then delete captured file. Serializing uploads/removals on one User row makes concurrent replace/replace and replace/remove converge on the last committed pointer without deleting a newer version; immutable keys must never be reused.

`LocalFileSystemStorage.save` currently uses a temporary file and `os.replace`, which prevents a partial final object during ordinary process failure, but it does **not** call `fsync` on the file or parent directory. PostgreSQL and the filesystem do not share a transaction. A crash after save but before DB commit can leave an unreferenced new file; a crash after commit but before old deletion can leave an unreferenced old file. A power loss can additionally challenge durability of an `os.replace` that was not synced. The first implementation must either add narrowly scoped durable avatar-write handling or document/test the accepted power-loss window before claiming the old-avatar availability guarantee. A response lost after DB commit leaves the client uncertain; refetch `/auth/me` instead of assuming rollback.

Use a **bounded, auditable avatar-only reconciliation** path for orphan recovery: enumerate only canonical keys under the avatar namespace, refuse symlinks and malformed keys, compare against current User pointers in a verified database snapshot, apply a grace period (recommended **24 hours**) and a per-run deletion cap, and support a dry run before deletion. Coordinate it with writers so an in-progress file is not removed. The current StorageProvider has no listing API and no durable cleanup queue; implementing a scoped enumerator or explicit cleanup ledger is a follow-up dependency, not an invitation to sweep the whole storage root. Missing current object maps to image 404 plus an internal repair signal; never expose the key or physical path in API output.

The inspected Compose mount persists PostgreSQL but declares no backend/avatar storage mount. Before enabling uploads, verify the actual backend's writable persistent root, restrictive filesystem ownership, free-space limits, backup/restore of avatar files **together with** database pointers, and behavior across restart/deployment. Do not treat a container's ephemeral directory or the PostgreSQL volume as avatar persistence. This is a deployment decision/gate, not an audit change.

## Bounded implementation and verification handoff

1. **Foundation:** Add the nullable User column and migration, strictly generated/parsed avatar keys, URL derivation, own `UserResponse.avatar_url` and storage-specific bounded/durable image operations. Verify legacy nulls, no fake backfill, downgrade refusal with live references and unchanged profile PATCH allowlist.
2. **Avatar API:** Add a separate multipart/DELETE mutation wrapper and authenticated media read. Reuse corrected Origin/private/session helpers without making profile/password accept multipart. Implement actual Pillow decode/canonical JPEG and User-row-locked save/replace/remove with post-commit restricted cleanup. No community permission dependency.
3. **Isolated checks:** With temporary storage and isolated API DB, test owner-only mutation, no-membership/banned owner, guest/revoked GET denial, authenticated exact-version image access, stale/missing/invalid-version 404, strict multipart fields/duplicate headers, declared and streamed limits, MIME spoofing, corrupt/truncated/bomb/animated/SVG inputs, EXIF rotation, alpha/metadata stripping, output caps, generic/private errors, idempotent removal and initials fallback metadata. Assert sessions, UUID, email/names, memberships/applications, permissions and authored-content links remain unchanged.
4. **Guarded PostgreSQL lifecycle:** Use only fresh marked disposable schemas, independent connections, row-lock barriers and temporary avatar storage. Exercise two replacements and replacement/removal races; assert final DB pointer refers to a present canonical file, loser/old-version behavior, no stale-hash/profile overwrite, rollback preserving old pointer/file, injected write/commit/cleanup failures, unrelated users' avatars untouched and cleanup limited to verified avatar-owned files. Never use owner/production data, a fixed-database truncation fixture or the development database.
5. **Frontend integration (later):** Add `avatar_url` to the actual EtudSup `AuthContext.User`; use existing username `accountInitials` for null/loading/error. Submit `FormData` with only `file` through credentialed `fetchApi` (let the browser set multipart boundary), refresh shared auth state on confirmed 200, and swap the versioned URL. Use an authenticated image load with the correct API cookie; avoid a Next image optimizer/public static URL that drops credentials or caches across users. Keep the existing account controls/theme treatments and accessible keyboard upload/remove feedback. A separate content task decides which author surfaces gain minimal avatar metadata.
