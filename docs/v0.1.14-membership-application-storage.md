## Current request and persistence flow

`POST /api/v1/communities/{community_slug}/membership` accepts the existing `MembershipCreate` schema, whose only field is required `cne` ([`schemas/membership.py`](../backend/app/schemas/membership.py#L7), [`endpoints/communities.py`](../backend/app/api/v1/endpoints/communities.py#L20)). It passes that value to `create_membership_request`.

The service rejects a globally conflicting PENDING or ACTIVE membership; a BANNED row cannot reapply. A prior REJECTED or REMOVED row is reused, reset to PENDING/MEMBER, and has its CNE and `updated_at` changed. Otherwise it creates a PENDING/MEMBER row ([`services/membership.py`](../backend/app/services/membership.py#L80)). This task leaves that behavior unchanged. Delegate appointment likewise continues to operate on existing rows or create an ACTIVE/DELEGATE membership using its existing CNE rules ([`services/provisioning.py`](../backend/app/services/provisioning.py#L72)). No applicant values are inferred by either path.

The existing delegate pending response explicitly projects the existing `cne`, account `username`, `first_name`, and `family_name`; it does not serialize Membership wholesale ([`services/membership.py`](../backend/app/services/membership.py#L330), [`schemas/membership.py`](../backend/app/schemas/membership.py#L22)). Public/member directory schemas are separate projections ([`schemas/membership.py`](../backend/app/schemas/membership.py#L59)). This foundation does not expose new fields through those responses. The preexisting pending-review CNE exposure remains unchanged and should be considered in the later API/privacy review.

## Storage and legacy compatibility

All new submitted application values belong on `Membership`, because they describe an application within a community. `User.first_name` and `User.family_name` remain account-level values; the new `applicant_first_name` and `applicant_family_name` capture the names submitted for that application without overwriting account identity. The existing `cne` column remains the sole student-identifier storage; no duplicate identifier column was added.

| Membership field | Meaning | Legacy representation |
| --- | --- | --- |
| `applicant_type` | `STUDENT`, `LAUREATE`, or database `NULL` | `NULL` means no new application details were submitted |
| `applicant_first_name` | Submitted application first name, up to 100 characters | `NULL` |
| `applicant_family_name` | Submitted application family name, up to 100 characters | `NULL` |
| `promotion` | Optional submitted Laureate promotion/year text, up to 20 characters | `NULL` |
| `cne` | Existing student identifier storage, up to 50 characters | Existing values retained; column now nullable for future Laureate rows |

There are no defaults or cross-field completeness constraints. Existing IDs, CNE values, statuses, roles, permission rows, community/user links, and timestamps are untouched by the migration. Names are not copied from `User`, and types are not inferred from roles, CNE, or other data. Downgrade drops all four new columns, so it discards application data written after upgrade; it first counts NULL-CNE rows and raises a clear error before schema changes if any exist, because the old schema requires CNE. It never fills identifiers or deletes rows.
