## 3. Initial Inspection Findings

- **Membership Model & Statuses**: Previously defined `PENDING`, `ACTIVE`, `REJECTED`. Role: `MEMBER`, `DELEGATE`, `MODERATOR`.
- **Global Uniqueness Index**: Partial index `uq_memberships_global_active_pending` on `user_id` where `status IN ('PENDING', 'ACTIVE')`. Rows in `REMOVED` or `BANNED` status do not satisfy this condition and therefore do not occupy the single active/pending slot.
- **Target Lookup & Uniqueness**: `uq_memberships_user_community` ensures at most one membership row exists per user per community. Reapplication mutates the existing row rather than generating conflicting rows.
- **Locking Order**: All existing membership services follow the strict locking sequence: `User` row (`FOR UPDATE`) -> `Membership` row (`FOR UPDATE`). Adhering to this order mathematically prevents deadlocks.
- **Audit System**: Table `management_events` created in `a916c0e16b01` had an unqualified unique constraint `uq_management_events_removal_target` on `(community_id, action, target_type, target_id)`. Without migrating this to a partial index, any member who was removed, reapplied, was approved, and removed again would trigger a unique constraint violation.
- **WebSocket Revalidation**: Handled in `check_ws_auth()` which validates `membership.status == MembershipStatus.ACTIVE`. As soon as status is updated to `REMOVED` or `BANNED`, periodic revalidation returns false and invokes `conn.close_and_cleanup()`.
- **Database Safety Guards**: Live tests assert `current_database() == "irm_integration_test"`, refuse any other connection, and execute tests within dedicated disposable schemas.

## 5. Endpoint Contract

All routes require authentication and an active Delegate in the community specified by `{community_slug}`.

| Method | Path | Summary | Success Status | Cache Header |
|---|---|---|---|---|
| `DELETE` | `/api/v1/communities/{community_slug}/memberships/{membership_id}` | Remove target from community | 204 No Content | `Cache-Control: private, no-store` |
| `PUT` | `/api/v1/communities/{community_slug}/memberships/{membership_id}/ban` | Ban target from community | 204 No Content | `Cache-Control: private, no-store` |
| `DELETE` | `/api/v1/communities/{community_slug}/memberships/{membership_id}/ban` | Unban target from community | 204 No Content | `Cache-Control: private, no-store` |

### Authorization Errors:
- `401 Unauthorized`: Guest or missing/invalid session cookie.
- `403 Forbidden`: Authenticated user without active Delegate status in `{community_slug}`.
- `404 Not Found`: Unknown community, unknown membership, foreign community membership, or malformed UUID.
- `409 Conflict`: Target is the acting Delegate (self-mutation), target role is `DELEGATE`, or invalid state transition.

## 6. State Transition Table

| Initial Target State | REMOVE Action (`DELETE .../memberships/{id}`) | BAN Action (`PUT .../memberships/{id}/ban`) | UNBAN Action (`DELETE .../memberships/{id}/ban`) |
|---|---|---|---|
| `ACTIVE` (Member) | -> `REMOVED` (Role reset to `MEMBER`, permissions purged, 1 event created, 204) | -> `BANNED` (Role reset to `MEMBER`, permissions purged, 1 event created, 204) | 409 Conflict |
| `ACTIVE` (Moderator) | -> `REMOVED` (Role reset to `MEMBER`, permissions purged, 1 event created, 204) | -> `BANNED` (Role reset to `MEMBER`, permissions purged, 1 event created, 204) | 409 Conflict |
| `ACTIVE` (Delegate) | 409 Conflict (Protected leadership) | 409 Conflict (Protected leadership) | 409 Conflict (Protected leadership) |
| `PENDING` | -> `REMOVED` (Role reset to `MEMBER`, 1 event created, 204) | -> `BANNED` (Role reset to `MEMBER`, 1 event created, 204) | 409 Conflict |
| `REJECTED` | -> `REMOVED` (Role reset to `MEMBER`, 1 event created, 204) | -> `BANNED` (Role reset to `MEMBER`, 1 event created, 204) | 409 Conflict |
| `REMOVED` | 204 No Content (Idempotent repeat, 0 events created) | -> `BANNED` (Role reset to `MEMBER`, 1 event created, 204) | 204 No Content (Idempotent repeat, 0 events created) |
| `BANNED` | 409 Conflict (Removal must not bypass a ban) | 204 No Content (Idempotent repeat, 0 events created) | -> `REMOVED` (Requires fresh reapplication, 1 event created, 204) |

### Reapplication Rules:
- **From `REMOVED`**: User may call `POST /api/v1/communities/{slug}/membership`. Transitions row to `PENDING` with role `MEMBER`.
- **From `BANNED`**: Application attempt returns HTTP 403 Forbidden with detail `"User is banned from this community."`.
- **From `UNBANNED` (now `REMOVED`)**: Eligible to submit fresh application (`PENDING`, `MEMBER`), subject to platform-wide single active/pending membership restriction.
- **Moderator Privileges**: Old permissions and moderator roles are purged upon removal/ban and never restored on reapplication.

## 7. Audit Event Behavior

Audit records are saved in `management_events`:
- **Columns**: `id`, `community_id`, `actor_id`, `action`, `target_type`, `target_id`, `created_at`.
- **Action Values**: `"remove"`, `"ban"`, `"unban"`.
- **Target Type**: `"membership"`.
- **Target ID**: The UUID of the target `memberships` row.
- **Actor ID**: The UUID of the acting Delegate (`users.id`). Set to NULL if actor is deleted (`ON DELETE SET NULL`).
- **Privacy & Sanitization**: Management events contain **metadata only**. No names, emails, CNE/Massar numbers, passwords, sessions, or content payloads are copied into `management_events`.
- **Transition Count**: Exactly 1 event is created per state transition. Idempotent repeats create 0 additional events. Legitimate multi-cycle transitions (e.g. remove -> reapply -> approve -> remove again) each create their own distinct transition event.

## 9. Concurrency, Atomicity, and Locking

1. **Locking Order**: `Target User` -> `Target Membership`. Consistent across `create_membership_request`, `approve_membership`, `reject_membership`, `withdraw_membership_request`, `transition_membership_role`, and delegate member mutations.
2. **Actor Authority Revalidation**: Checked within the transaction on `Membership` table to ensure an actor demoted during a competing transaction cannot commit a member mutation.
3. **Atomic Failure Rollback**: Pre-commit failure rolls back status mutation, permission deletion, and management event creation together.
4. **Race Resolution**:
   - Ban vs Reapplication: Serialized via user row lock; in all ordering permutations, the banned user ends in `BANNED` state (never active or pending).
   - Ban vs Approval: Serialized via user and membership locks; approval cannot bypass a committed ban.
   - Concurrent Identical Calls: Serialized via membership lock; first caller mutates and logs event, subsequent callers observe target already in final state and return idempotent 204 with 0 additional events.

## 10. WebSocket Revocation Timing

- **Enforcement Mechanism**: Periodic background revalidation loop in `discussion_websocket`.
- **Maximum Revocation Latency**: Up to **30 seconds** (`WS_REVALIDATION_INTERVAL_SECONDS = 30`).
- **In-flight Queue Bound**: **100 messages** (`WS_QUEUE_MAX_SIZE = 100`).
- **Revocation Sequence**:
  1. Background loop executes `check_ws_auth(raw_token, community_slug)`.
  2. Membership status `REMOVED` or `BANNED` triggers `valid = False`.
  3. `Connection.close_and_cleanup()` is invoked:
     - Sets `conn.closed = True` (halts any subsequent incoming `enqueue`).
     - Cancels `sender_task` and `revalidation_task`.
     - Drains all pending queued frames.
     - Closes WebSocket with code `1008` (`WS_1008_POLICY_VIOLATION`) and reason `"Session expired or membership revoked"`.
     - Unregisters connection from broadcaster pool.
