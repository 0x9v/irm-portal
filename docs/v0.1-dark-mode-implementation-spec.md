## 1. Evidence and current architecture

Read root `AGENTS.md` and `frontend/AGENTS.md`; inspected `git status --short` before work. The tree already contains extensive modified/untracked application files and `docs/v0.1-dark-mode-audit.md`. That existing document was preserved; this separate document is based on current source, not its conclusions.

**Source inspection:** enumerated all 19 `frontend/src/app/**/page.tsx` files; read route rendering/state branches, shared presentation, auth/session lifecycle, reader rendering constraints, discussion assets, CSS/Tailwind mappings, configuration, and relevant test fixtures/assertions. Repository-wide searches covered colour literals, palette utilities, inline styles, SVG fills/strokes, theme/storage/CSP declarations, and route files. This is not a claim of line-by-line inspection of every asynchronous branch, backend, generated worker, dependency, or test. No production headers were fetched.

- [`frontend/src/app/globals.css`](../frontend/src/app/globals.css): sole application CSS file. `:root` defines page/surface/text/border/accent/feedback/disabled/focus tokens. Tailwind v4 `@theme inline` maps these to `--color-*`; `@theme` defines radius/shadow utilities. Preserve Tailwind's standard palettes; do not globally redefine `white`, `gray`, `red`, etc.
- [`frontend/src/app/layout.tsx`](../frontend/src/app/layout.tsx): server root layout, `<html lang="en">`, token-styled body → `AuthProvider` → `ApplicationShell`. No theme attribute, provider, bootstrap, or colour-scheme declaration exists. `communities/irm/layout.tsx` is a width wrapper, not a separate theme boundary.
- [`frontend/src/components/layout/ApplicationShell.tsx`](../frontend/src/components/layout/ApplicationShell.tsx): client shell, 248px sticky desktop sidebar and context bar at **1280px (`xl`)**, mobile/tablet header/disclosure below 1280px; sidebar hide/show is local state. Keep this architecture and breakpoint.
- `frontend/src/context/AuthContext.tsx`: auth, membership, capability verification, refresh, and logout; logout clears session state after success/already-logged-out 401, preserves session on failure. No storage-backed theme mechanism to reuse. Keep theme independent of this provider's lifecycle.
- `frontend/package.json`, `postcss.config.mjs`: Next 16.3.6, React 19.2.8, Tailwind v4, PDF.js 4.10.x; no theme/forms library. Existing React, DOM APIs, and CSS variables are sufficient.
- `frontend/next.config.ts` is empty configuration; no `proxy.ts`/middleware found in frontend inventory. Searches of frontend source/config and the sole `deploy/frontend.Dockerfile` found no CSP. An upstream production CSP remains **unverified**.
- Installed Next guides inspected: `frontend/node_modules/next/dist/docs/01-app/02-guides/preventing-flash-before-hydration.md` (Themes), `.../content-security-policy.md`, and `.../03-api-reference/02-components/script.md`. The installed guide recommends synchronous head bootstrap for theme before paint; an effect-only initialization flashes. No initialization code was written.

**Readiness:** most ordinary cards, headings, breadcrumbs, guidance, feedback, inputs, and navigation already use tokens. Remaining risks are role/hero CSS literals, palette utilities in exceptional states, mixed text/action tokens, low-contrast control borders, white ring offsets, opacity-disabled text, native controls, and reader/sticker exceptions.

## 4. Proposed palette and token contract

Dark direction: aubergine page, three separated content levels, soft off-white text, muted lavender-grey text, blue-violet accents, green/amber/red/blue feedback. No pink drift, all-black UI, blanket inversion, new gradients, glow, animation, shadows, or spacing changes.

Keep current light root values. Add dark overrides on `html[data-theme="dark"]`; extend `@theme inline` with semantic mappings for new colour tokens. Token names below omit the `--` prefix. `accent*` becomes **text/line/icon colour**; all filled primary actions and selected filled chips must use `action*` with `on-accent`. The brand gradient needs a fixed start (`#6D28D9`), not the bright dark text accent. Success/error text similarly must not double as action backgrounds.

## 5. Calculated contrast and limits

Calculated in Python during this audit from source hex values with sRGB relative luminance: linear channel = `c/12.92` for `c ≤ 0.04045`, otherwise `((c+0.055)/1.055)^2.4`; luminance = `0.2126R + 0.7152G + 0.0722B`; contrast = `(Llighter+0.05)/(Ldarker+0.05)`. Actual Tailwind OKLCH values were converted to linear sRGB (out-of-gamut channels clamped to 0–1) for the specific baseline action checks below. Alpha colours require compositing over the actual underlying surface; the opaque-token calculations do not certify existing alpha utilities.

Target: normal text ≥4.5:1; large text and applicable non-text boundaries/state indicators ≥3:1. Never round a below-threshold value up to a pass. Colour calculations alone do **not** establish formal WCAG conformance, keyboard accessibility, usability, or readable art.

## 6. Exact theme integration strategy for the next task

No new dependency, auth API, cookie, backend field, or migration is needed.

1. **Root ownership:** resolved theme belongs on `document.documentElement` as `data-theme="light"` or `"dark"`. Optional `data-theme-preference="system|light|dark"` distinguishes preference from resolution and is not sensitive. `globals.css` owns light defaults and dark variable overrides. Root HTML background follows `page` so overscroll/unpainted regions match. In addition to explicit attributes, a `prefers-color-scheme: dark` fallback applies only when no resolved attribute exists, so no-JS/System boot can render dark without overriding explicit Light.
2. **Storage contract:** one versioned origin-local key, `irm.theme.preference.v1`; plain exact string `light`, `dark`, or `system`. Missing, unknown, wrong-case, JSON/object text, empty/corrupt value → System. Store only this preference. No account ID, membership/capability, document, draft, messages, token, or protected content. Preference is browser/device-local and shared across accounts on that browser. Persist System as `system` (or treat removed key as System consistently); recommend the explicit string for one clear contract.
3. **Before-paint initialization:** a small static synchronous inline head script in **`frontend/src/app/layout.tsx`**, before body content, validates stored preference in a guarded read and resolves System via `matchMedia('(prefers-color-scheme: dark)')`. Set the resolved HTML attribute before paint. Storage read failure must still resolve System; do not put media resolution only inside a storage try block that can skip it. If media query access is unavailable, fall back safely to Light. No app fetch, redirect, content serialization, body hiding, async theme fetch, or theme initialization code is included in this audit.
4. **Hydration:** retain server root layout. Limit `suppressHydrationWarning` to `<html>` for the bootstrap-owned theme attributes; do not apply it to route content. Planned client `frontend/src/context/ThemeContext.tsx` wraps **outside `AuthProvider`**, so auth/logout/route transitions cannot reset theme. Its SSR and first client render use identical neutral state (`ready=false`, preference System); after mount adopt the bootstrap preference/resolution and reconcile storage/media. Route content must not conditionally render different markup by resolved theme. Theme changes update attributes/variables only. The selector has identical initial markup, disabled until preference is known, then displays the actual preference. Do not initialize client JSX from localStorage in render. Leave existing date/locale behavior alone.
5. **Runtime changes:** provider centralizes validation/resolution; Light/Dark ignore subsequent OS changes, System follows them through a cleaned-up media-query change listener. Set attributes immediately when the selector changes, then attempt a guarded persistence write. Write failure retains the chosen in-memory theme for this navigation session; render continues, and after reload storage-unavailable behavior returns to System. Do not promise persistence when the browser forbids storage. A storage event from another tab (including key removal or corrupt value) is recommended to reconcile this device preference; it should not write back in a loop. Do not write a default preference before initial read, which would overwrite a saved selection.
6. **Selector placement:** planned reusable `frontend/src/components/ui/ThemeSelector.tsx`, labelled native select with Light / Dark / System and at least 44px height. Place in **desktop `navigation/ContextBar.tsx`** beside existing context controls, accessible while the sidebar is hidden; do not depend on the account being loaded. Place a second instance below the navigation groups and before the account section in the existing **`navigation/MobileHeader.tsx` disclosure**; show it to guests as well as authenticated users. Use distinct IDs/label associations for simultaneously mounted desktop/mobile instances. Both consume one provider. Change should not close the mobile disclosure unexpectedly, navigate, or submit a form. Preserve keyboard/native selection and visible selected preference; “System” remains selected when its resolved scheme is Dark. Do not reactivate legacy Header.
7. **CSP:** no repo policy was found, so the static inline head approach fits the inspected source. Before implementation rollout, inspect the actual document response headers in a permitted environment. If an upstream strict policy exists, authorize the exact static bootstrap with a CSP hash, or use an already-existing nonce contract. Never add `unsafe-inline` solely for theme. Adding a per-request nonce/dynamic rendering/proxy would be an architectural/deployment decision to flag, not silently implement. Blocked bootstrap should still have CSS System fallback and safe provider initialization, though explicit-preference flash must then be tested/resolved.
8. **Native scheme:** CSS `color-scheme: light` for resolved Light, `dark` for resolved Dark and matching System fallback, inherited by native selects, checkboxes, scrollbars, autofill and validation UI. Keep PDF paper backing explicitly Light if needed for its fixed white context, without touching the text layer. Do not use global `color-scheme: light dark` when explicit Light is selected; that would leave UA choice inconsistent.
