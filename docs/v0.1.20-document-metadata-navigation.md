# Task 0.1.20 — Document Metadata and Return Navigation

## Existing contract and visibility

The module page is `frontend/src/app/communities/irm/modules/[moduleSlug]/page.tsx`; it fetches the module metadata and approved document list separately (module request near line 84; list request near lines 123–125). The backend list route is `GET /api/v1/communities/{community_slug}/modules/{module_slug}/documents` in `backend/app/api/v1/endpoints/documents.py:66–100`; it remains authenticated and approved-only, with optional `q`, `type`, and `source`. `DocumentResponse` already contains title, type, source, status, and timestamps (`backend/app/schemas/document.py:6–17`), but the ordinary list intentionally does not display a status badge.

The existing detail page at `frontend/src/app/communities/irm/modules/[moduleSlug]/documents/[documentId]/page.tsx` fetches the same approved-only module detail route and renders `DocumentReader`. The reader and its zoom, selection, page, and download behavior were not changed. The module page already linked to detail; detail previously returned only to the module route and had a second generic “All Modules” link. A direct visit could reach the module, but there was no contextual return to My Submissions or the pending queue. Module `q`/`type`/`source` state was held only in React state, so it did not survive leaving and returning.

The pending review page (`frontend/src/app/communities/irm/documents/pending/page.tsx`) receives title, module slug/name, type, source, status, and submission time. Its permitted pending preview and existing review controls are unchanged. It did not previously link the module name. The private My Submissions page (`frontend/src/app/communities/irm/documents/mine/page.tsx`) receives module name/slug, title, type, source, status, and timestamps. It already links approved submissions to the reader, permits only its existing pending preview, and offers no file action for rejected documents. Its existing active-membership gate and backend authorization are unchanged.

The approved detail route remains the only reader entry introduced here. Pending queue items point to their module list and can use the existing preview; no pending item is linked to the approved detail route. The My Submissions approved link carries a safe internal context. Rejected rows retain no detail, preview, or download action.

Persona visibility is unchanged: guests cannot use the authenticated module list/detail routes; any authenticated user can see APPROVED documents in a module list/detail, independent of membership; pending/rejected rows are absent from those routes. The pending queue endpoint requires an ACTIVE membership in the requested community and lists PENDING student-source documents with the existing caller-specific voting/access response fields. My Submissions requires the caller’s ACTIVE membership and returns only that caller’s own records across modules. Existing vote controls continue to depend on the queue response’s authorization flags.

The module list remains a simple array (no pagination/cursor); its order and filter behavior are unchanged. The pending queue is also a simple array and already returns `private, no-store`; its response schema is `PendingDocumentResponse` (`backend/app/schemas/document.py:22–39`). My Submissions uses `{items, next_cursor}` with the existing bounded cursor contract (`backend/app/api/v1/endpoints/documents.py:103–146`, response schema `backend/app/schemas/document.py:42–57`) and private no-store caching. No list count, cursor, or status filter was added by this task.

## Implementation

`frontend/src/lib/documentPresentation.ts` adds the shared labels and URL-state helpers. Existing enum values remain unchanged:

| Stored value | Display label |
| --- | --- |
| COURSE | Course |
| TD | Tutorial |
| TP | Practical work |
| EXAM | Exam |
| SOLUTION | Solution |
| OTHER | Other |
| OFFICIAL | Official |
| STUDENT | Student submission |

Existing statuses are labeled `PENDING` → “Awaiting review”, `APPROVED` → “Approved”, and `REJECTED` → “Not approved”. Type/source labels now appear consistently in the module list, approved detail, pending review queue, and My Submissions. Status appears only in the authorized pending queue and the applicant’s own submissions page. Existing dates are retained in each context. No author, reviewer, UUID, storage path, vote detail, or approval badge was added to the approved-only list.

Return context is carried only as `from=module`, `from=mine`, or `from=pending`; arbitrary `returnTo` values are ignored. Missing, invalid, or unsupported context returns to the document’s actual module route. A direct detail visit therefore always has a module link. My Submissions’ module and approved-reader links use `from=mine`; a pending queue module link uses `from=pending`, which is carried through an approved document opened from that module. Contextual breadcrumbs and the single visible return button use the same destination. The pending/rejected file gates are unchanged.

The module page serializes only validated `q`, `type`, and `source` values into its URL, using the existing type/source enums and the existing 100-character trimmed query limit. It initializes the controls and request from validated URL state and uses the existing backend search semantics. Detail links carry that module state back; returning to the module restores the selections and requests the corresponding approved list. No localStorage or new backend behavior was added.
