## 2. Root Cause of Local HTTP 500 Errors

In subtask 0.1.6, soft-removal moderation metadata (`removed_at`, `removed_by_id`) was added to SQLAlchemy models (`Announcement`, `AnnouncementReply`, `CommunityPost`, `CommunityPostReply`, `DiscussionMessage`), and migration `a916c0e16b01` was drafted following revision `f8c2b3d4e5f6`.

Because 0.1.6 was executed and verified solely against SQLite in-memory fixtures (due to an environment permission error when attempting to spawn a temporary PostgreSQL Unix socket cluster), migration `a916c0e16b01` had never been applied to the local development database (`irm_platform` on port 5433).

When read requests were executed:
- `GET /api/v1/communities/irm/announcements?limit=3`
- `GET /api/v1/communities/irm/posts?limit=20`

SQLAlchemy generated queries with `WHERE announcements.removed_at IS NULL` and `WHERE community_posts.removed_at IS NULL`. Because the columns did not exist in the database, PostgreSQL raised:
- `column announcements.removed_at does not exist`
- `column community_posts.removed_at does not exist`

causing unhandled exceptions resulting in HTTP 500 responses.

## 6. WebSocket Moderation Acceptance

Tested using an isolated uvicorn test process on an unused loopback port connected to `irm_integration_test` in `backend/tests/api/v1/test_moderation_websocket_pg.py`:

- **Broadcast delivery**: Two clients subscribed to `irm` received `message_removed` event.
- **Community isolation**: Client subscribed to `foreign` community received zero events.
- **Metadata minimization**: Event payload contains strictly:
  ```json
  {"type": "message_removed", "community_slug": "irm", "message_id": "<UUID>"}
  ```
  No body text, sticker data, or actor identity included.
- **Commit ordering**: Event broadcast occurs only after DB commit; rolled back operations emit zero events.
- **Repeat suppression**: Repeated removal of already removed message emits no second broadcast.
- **Broadcast resilience**: Broadcaster failure is caught and logged; it does not undo committed database removal.
- **Queue purging**: Enqueueing `message_removed` purges matching pending `message_created` events from subscriber queues.
- **Pre-send visibility**: Short-lived DB check before transmission drops payloads if message became removed while queued.

### In-Flight Socket Ordering Limitations
- **Guaranteed**: If a message has not yet been dispatched by the socket loop, the visibility check suppresses it. If a message is pending in the in-memory queue, enqueueing removal purges it. All subsequent REST history reads exclude it.
- **Limitation**: Bytes already dispatched to the TCP kernel buffer cannot be retracted from the network. Reconnection catch-up requires REST history resync rather than durable pub/sub outbox replay.

Suite result: **6 passed** in 3.30s.
