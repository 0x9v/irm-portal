# v0.1 — Subtask 0.1.6: Delegate content moderation backend

## Implemented scope and inspection

Implemented backend soft removal for announcements, announcement replies,
community posts, post replies, and discussion messages (both TEXT and STICKER).
No frontend controls, restoration, removed-content browsing, announcement editing,
account deletion, member management, or document moderation were added.

The existing HTTP-only session dependency and `require_community_delegate` already
enforce an ACTIVE membership with the exact DELEGATE role in the requested
community. They are reused without changes. Moderator grants such as
CREATE_ANNOUNCEMENTS and MANAGE_DOCUMENT_VOTING are deliberately insufficient.
Content authority is resolved before looking up the target record.

Inspected the five models and their schemas, services, REST routers, membership
dependencies and grants, reply/feed cursors, discussion replay uniqueness,
reaction aggregation, WebSocket sender queues and reconnect history, Alembic
history, and test fixture setup. No additional related search/count API was found.
Visible-content response schemas remain unchanged. Existing batched reaction
queries and eager author/module loading remain; no per-item read query was added
to list endpoints.

## Routes and authorization

All five operations are DELETE:

```text
/api/v1/communities/{community_slug}/announcements/{announcement_id}
/api/v1/communities/{community_slug}/announcements/{announcement_id}/replies/{reply_id}
/api/v1/communities/{community_slug}/posts/{post_id}
/api/v1/communities/{community_slug}/posts/{post_id}/replies/{reply_id}
/api/v1/communities/{community_slug}/discussion/messages/{message_id}
```

| Caller / target | Status |
| --- | --- |
| Missing, expired, invalid, or revoked session | 401 |
| Non-member, pending/inactive member, ordinary member | 403 |
| Moderator, including one with all existing grants | 403 |
| Delegate of another community without target authority | 403 |
| ACTIVE target-community Delegate; visible target | 204, empty body |
| Same authority; already removed target | 204, empty body; original actor/time retained |
| Same authority; unknown or cross-community target | 404 |
| Reply belongs to another parent, or parent unavailable/removed | 404 |
| Malformed UUID | Existing FastAPI 422 validation contract |

Content responses carry `Cache-Control: private, no-store`. Repeat reply removal
requires its parent to remain available, as required by the parent policy.

## Visibility, pagination, replay, and transactions

Announcement lists/latest/detail, post feeds/excerpts/detail/module filters,
reply lists, and all discussion latest/older/newer history filter removal in SQL
before LIMIT/lookahead. Existing `(created_at, id)` ordering and limits remain.
The existing optional announcement-list limit contract remains unchanged.

Parent removal hides its detail and reply APIs and blocks new replies. Child rows
are preserved without being rewritten. Individual reply removal hides only that
reply. Cursor validation reads only `(created_at, id)` and accepts removed records
in the correct community/parent (and the existing post module scope). It never
returns their bodies. Unknown/foreign reply and post cursors remain 400;
unknown/foreign discussion cursors remain 404; malformed UUIDs remain 422;
simultaneous discussion before/after cursors remain 400. Removed parents still
make their reply APIs unavailable.

Discussion retry uniqueness is unchanged. Both the normal replay path and
IntegrityError recovery reject a removed retry record with a safe 409 before
returning original payload. TEXT and STICKER use the same removal policy.
Removed messages reject reaction PUT/DELETE with 404. Existing reaction rows may
remain but are not exposed through removed-message history or reaction endpoints.

Removal uses a scoped conditional UPDATE with `removed_at IS NULL`. Only the
winning update inserts an event, in the same transaction. A repeat checks only
the scoped record's existence and returns success without changing metadata or
creating an event. Any state/log failure rolls back both. Reply creation and
individual reply removal lock the visible parent; reactions and replay lock the
message. These mutations never set removal fields back to NULL. Fresh checks
after commits and before broadcasts reject stale creation/reaction results.

Management events use action `remove` and target types `announcement`,
`announcement_reply`, `community_post`, `community_post_reply`, and
`discussion_message`. The log contains no bodies, applicant identity, passwords,
or tokens. No log-listing API was added. A later management view will need its own
community-scoped authorization, bounded pagination, and display contract; this
task grants no Moderator access to it.

## WebSocket contract and limits

After a first successful discussion removal commits, the existing broadcaster
receives exactly this community-scoped event:

```json
{"type":"message_removed","community_slug":"irm","message_id":"<UUID>"}
```

It contains no original text, sticker payload, actor identity, or personal
reaction information. Repeats do not rebroadcast. Broadcast failure is logged
without the original payload and cannot roll back committed removal.

Enqueuing removal purges matching pending message_created/reaction_changed
events while preserving other queued event order and bounded queue accounting.
Production senders also perform a fresh, scoped, short-lived DB visibility check
before each content/reaction send. This suppresses late queued creation events
even after a removal event was processed. Visibility-check failure drops that
payload rather than exposing potentially removed content. Ordinary reconnect
history uses the filtered REST path.

Limits: bytes already in flight cannot be recalled. There remains a small gap
between the final visibility check and the socket write, and an ordinary read
already in progress can observe its earlier visibility snapshot. No global
transaction/socket ordering protocol was added. The existing broadcaster is
single-process/single-worker; there is no distributed event bus or durable
removal-event replay/outbox. Existing created_at-versus-commit-order reconnect
limitations remain. A failed broadcast or missed removal event requires a fresh
visible REST history resync. An after-cursor catch-up alone does not tell a client
which previously cached messages were removed. Frontend event handling and cache
reconciliation belong to the later frontend subtask.
