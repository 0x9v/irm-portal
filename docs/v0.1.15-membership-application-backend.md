## Request and response contracts

The endpoint remains `POST /api/v1/communities/{community_slug}/membership`. Existing clients may continue to send the temporary legacy request shape:

```json
{"cne":"CNE12345"}
```

That path preserves the existing CNE string coercion and membership lifecycle, does not infer an applicant type or names, and clears any stored new application values during reapplication. It does not enforce new applicant fields. Unknown fields are now rejected, as required for the documented request contract; for example, status, role, and user ID cannot be injected.

New Student/Massar request:

```json
{
  "applicant_type":"STUDENT",
  "applicant_first_name":"Élodie O'Neil-Smith",
  "applicant_family_name":"Ben Ali",
  "identifier_type":"MASSAR",
  "cne":"r123456789"
}
```

The stored CNE becomes `R123456789`. A Foreign Student uses the same fields with `"identifier_type":"FOREIGN"`; for example, `"cne":"001234567"` remains unchanged. Identifier type describes the chosen identifier format, not nationality.

Laureate request:

```json
{
  "applicant_type":"LAUREATE",
  "applicant_first_name":"José",
  "applicant_family_name":"D'Arcy",
  "promotion":"23/24"
}
```

The stored promotion is normalized to `2023/2024`; stored CNE and identifier type are NULL. The UI sentinel strings `Older` and `Other` are invalid API values.

The POST endpoint retains its existing 201 response schema (membership ID, community ID, status, role, and timestamps). Private application details are retrieved from the applicant's authenticated `GET /api/v1/communities/{community_slug}/membership/me` response. The existing Delegate `GET /api/v1/communities/{community_slug}/membership/pending` response now includes nullable `applicant_type`, `applicant_first_name`, `applicant_family_name`, `identifier_type`, `promotion`, and nullable `cne`. Existing account `first_name`/`family_name` retain their meaning and remain distinct from the submitted applicant names. Both private responses use `Cache-Control: private, no-store`.

## Validation and policy

The request contract accepts exactly the legacy CNE-only form or a complete new form. Supplying any new application field selects the new contract; missing applicant type, partial names, unsupported enum values, contradictory fields, and unknown fields fail validation. New application strings must be strings.

Application names are trimmed, required, nonempty, and limited to 100 Unicode code points after trimming. Unicode names, accents, spaces, apostrophes, and hyphens are preserved. Control characters and line separators are rejected. These are applicant-submitted names, not independently verified identity data. They are saved to Membership and never overwrite User account names.

For Students, both `identifier_type` and `cne` are required and `promotion` must be absent or NULL. CNE is trimmed and remains the sole identifier-value storage. MASSAR accepts exactly one ASCII letter plus nine ASCII digits, uppercases the letter, and preserves digits including leading zeros. FOREIGN accepts 1–50 ASCII letters/digits, preserves case and zeros, and does not apply a country-specific passport format. Both types reject controls, internal whitespace, punctuation, and non-ASCII identifier characters. This checks supported input syntax; it does not verify identity or document authenticity.

For Laureates, names and promotion are required; CNE and identifier type must be absent or NULL. Promotion accepts ASCII `YYYY`, `YY`, `YYYY/YYYY`, or `YY/YY`. Two-digit years mean 20YY; pairs must have matching widths and consecutive years. Pairs normalize to `YYYY/YYYY`; standalone years normalize to `YYYY` and are treated as the graduation/end year. The end year cannot exceed the configured current academic-year start. There is no minimum graduation year.

`membership_current_academic_year_start` is the single backend policy setting, sourced from `MEMBERSHIP_CURRENT_ACADEMIC_YEAR_START`, default 2026, validated as an integer from 1000 through 9998 so the following year can be represented. No month/date rollover is inferred. With 2026 configured, the options endpoint returns exactly `2025/2026`, `2024/2025`, `2023/2024`, `2022/2023`, `2021/2022`, and `2020/2021`; future `2026/2027`, `26/27`, and standalone `2027` are rejected.

Authenticated options route:

```text
GET /api/v1/communities/{community_slug}/membership/application-options
```

Example response for the default policy:

```json
{
  "current_academic_year_start":2026,
  "applicant_types":["STUDENT","LAUREATE"],
  "student_identifier_types":["MASSAR","FOREIGN"],
  "promotion_options":["2025/2026","2024/2025","2023/2024","2022/2023","2021/2022","2020/2021"],
  "custom_promotion_formats":["YYYY","YY","YYYY/YYYY","YY/YY"]
}
```

It requires an authenticated user and a valid community slug, contains no applicant data, and is marked private/no-store.

## Migration and lifecycle

The additive revision is `98b4d2a6f731`, predecessor `d7a9b6c4e213`, current head `98b4d2a6f731`. `identifier_type` is nullable VARCHAR(20) with a check permitting only `MASSAR`, `FOREIGN`, or NULL. Existing rows remain NULL; no identifier type is inferred. The model and migration define the same length, nullability, and allowed values. No new cross-field database constraints were added because legacy rows remain valid with NULL application fields.

Creation persists all validated fields in the existing membership insert. Reapplying from REJECTED or REMOVED reuses the same row and replaces the entire application data set atomically: Student-to-Laureate clears CNE/identifier type, Laureate-to-Student clears promotion, and legacy reapplication clears every new field. Existing account names, ID, community association, creation time, lock order, global PENDING/ACTIVE uniqueness, BANNED denial, and approval/rejection/role/permission behavior are preserved. No automatic type transition or edit route was added.

## Privacy and authorization

| Surface | Access | Application details |
| --- | --- | --- |
| `GET .../membership/me` | Authenticated current user, membership scoped by their user ID and target community | Own membership's fields, including CNE; private/no-store |
| `GET .../membership/pending` | ACTIVE DELEGATE in the target community, enforced by the existing dependency | Pending applicants' details and existing account names; private/no-store |
| Application-options endpoint | Any authenticated user for an existing community | Policy only; no applicant values |
| Community membership directory and active-member response | Existing Delegate access | Explicit projection excludes CNE, applicant names/type, identifier type, and promotion |
| Public community, posts, announcements, discussions, author summaries, and management events | Existing access rules | No new application fields added |

Tests verify that another persona and a Delegate from another community cannot fetch pending details. No standalone backend staff-listing route was found in the inspected membership endpoints; existing directory and active-member projections remain explicit and private fields are excluded.
