### Actual member-list contract and missing integration

`GET /api/v1/communities/{community_slug}/membership/active` is Delegate-authorized and returns an unpaginated list filtered to ACTIVE memberships. `ActiveMembershipResponse` contains `id`, `status`, `role`, `created_at`, `updated_at`, `username`, `first_name`, and `family_name`. It includes ordinary members, moderators and Delegates. Existing staff identity presentation is retained; new actions use the actual membership ID and username and add no private identity fields.

`GET /api/v1/communities/{community_slug}/membership/pending` returns pending applications with their existing review fields. It remains connected to approval/rejection.

There is **no authorized list endpoint returning BANNED or REMOVED memberships, and no status-filter parameter that makes the active list return them**. Therefore active-member Remove/Ban are implemented in the existing staff roster, with an explicit ACTIVE-view explanation. Unban selection and additional status filters cannot be implemented honestly. No fake directory, speculative endpoint, retained private directory, or internal-UUID input was added. The Unban request specification and wording are implemented and tested as part of the eight real contracts, but no unusable Unban button is shown. A backend list contract exposing authorized banned-member selection is required to finish that UI.

## Implemented behavior

All five content controls are discreet labeled actions with semantic error styling, 44px minimum targets and visible focus. Announcement controls are siblings of the whole-card link. Post/detail/reply/message controls are outside headings, title links and reaction controls. Members, moderators, guests, unknown statuses, initial loading, refresh, logout and verification/session failures cannot expose them. AuthContext currently verifies only IRM; its authority is explicitly insufficient for any other slug.

The reusable native `dialog.showModal()` supplies modal isolation. Cancel receives initial focus; Tab is contained, Escape cancels only when no request/check is pending, and focus returns to the connected trigger or current page heading. The dialog is portaled above navigation, bounded to the viewport and scrollable. Pending locks use a ref as well as disabled buttons, preventing same-turn duplicate calls. Descriptions explain community visibility and parent reply hiding without claiming database erasure, offer no user-facing Undo for content, and require no moderation reason. Discussion confirmations identify author/time without copying the message body.

No local removal precedes confirmed success. On 204, list items are removed, both canonical and local-confirmed reply collections are reconciled, and removed parent details clear their parent and unmount all replies/drafts before displaying existing unavailable/return guidance. On 404, equivalent reconciliation includes unavailable feedback. On 401/403, the existing auth/membership refresh runs and the denied action hides immediately; observed access loss uses protected-content cleanup and closes dialogs. On 409, the server's leadership/state refusal is displayed without changing the row. Network/500 outcomes preserve content and explain that completion cannot be confirmed, offering Refresh and check plus an explicit retry. There are no automatic mutation retries.

Actions are keyed to account, membership, community and target. Mounted-request guards suppress completions after unmount, scope change or observed loss of confirmed Delegate authority. Read/submission guards also protect cleanup from delayed protected-content responses. Leaving a page or ignoring a completion does not prove that a backend mutation was cancelled or rolled back.

Member removal/ban clear the affected row from the ACTIVE-only roster after success, consistent with the documented REMOVED/BANNED transitions. Other rows and existing role/permission controls remain. Both acting and other Delegate rows have no Remove/Ban actions; backend 409 remains authoritative. A read begun before removal cannot restore its row; a fresh authoritative roster may display a legitimate later reapproved membership. Removal retains account/contributions and allows reapplication; a community Ban retains them while blocking access/reapplication. Unban transitions to REMOVED and permits a fresh application, never automatic activation/approval.

REMOVED guidance offers the existing CNE application action. BANNED guidance suppresses that form and links to Support, without fabricating a reason. Unknown statuses fail closed and show status-unavailable guidance. Existing PENDING/REJECTED behavior remains. Student/Laureate fields were not redesigned.

### Discussion races and revocation

The client accepts `message_removed` only with `community_slug: "irm"` and a string message ID, from its current scoped socket. Duplicate events are harmless. The combined canonical/live/local-confirmed message collection drops the item; unmounting the message closes its reaction picker, and its pending reaction presentation is removed. Late history, older-page, message-created, confirmed-send and reaction responses cannot restore an observed removal. Ordering, deduplication, idempotent submission/retry IDs, backend cursors, caller reaction isolation, scroll adjustment, backoff and existing reconnection history reconciliation are retained.

The removal ledger is account/community/mount-scoped and capped at 2,048 IDs. It clears on account change, access loss and unmount. At saturation, ingestion fails closed rather than evicting tombstones; the view requests a page reload and disables the composer until that fresh session. No tracking is persisted.

There is no global membership polling. Another user's action or an external cookie change needs an observable denial, membership refresh, or socket revalidation before React knows about it. Backend discussion authorization is revalidated periodically (up to 30 seconds under the documented interval), with policy-close 1008 and existing frontend revalidation. Zero-delay revocation and durable/cross-worker deletion-event delivery are not promised.
