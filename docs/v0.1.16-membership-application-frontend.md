## API contract used

The authority is [Task 0.1.15 membership application backend handoff](v0.1.15-membership-application-backend.md). The implementation uses these routes and shapes:

- `GET /api/v1/communities/irm/membership/application-options` (authenticated): `current_academic_year_start`, `applicant_types`, `student_identifier_types`, `promotion_options`, and `custom_promotion_formats`. Preset year choices come from this response. The page offers a separate custom-entry action and never submits a UI sentinel.
- `POST /api/v1/communities/irm/membership`:
  - Student: `applicant_type`, `applicant_first_name`, `applicant_family_name`, `identifier_type` (`MASSAR` or `FOREIGN`), and `cne`.
  - Laureate: `applicant_type`, `applicant_first_name`, `applicant_family_name`, and `promotion`.
  - The temporary legacy CNE-only shape remains a backend compatibility path, but this new form does not submit it.
- `GET /api/v1/communities/irm/membership/me` supplies the applicant's own private details in `membership`, including nullable `cne`, `applicant_type`, `applicant_first_name`, `applicant_family_name`, `identifier_type`, and `promotion`, alongside existing membership status/role/capabilities. Submission still returns the compact existing membership response, so AuthContext refreshes after success.
- `GET /api/v1/communities/irm/membership/pending` supplies Delegate review fields including application values and distinct account `first_name`, `family_name`, and `username`. The page retains the existing ACTIVE Delegate gate and review actions.
- Existing `fetchApi` parses FastAPI validation arrays from `detail` into `ApiError.details`; `formatFormError` maps those field locations for the form. A CNE-location error is presented as a student-identifier error so Foreign identifiers are not mislabeled as CNEs.

Representative request bodies (the page sends one of the two new shapes):

```json
{"cne":"LEGACY-CNE"}
```

```json
{"applicant_type":"STUDENT","applicant_first_name":"Rania","applicant_family_name":"Ben Ali","identifier_type":"MASSAR","cne":"R123456789"}
```

```json
{"applicant_type":"STUDENT","applicant_first_name":"Rania","applicant_family_name":"Ben Ali","identifier_type":"FOREIGN","cne":"001234567"}
```

```json
{"applicant_type":"LAUREATE","applicant_first_name":"Rania","applicant_family_name":"Ben Ali","promotion":"2023/2024"}
```

The existing POST success response stays compact. After AuthContext refresh, applicant details are read from a response shaped like:

```json
{"membership":{"id":"…","status":"PENDING","role":"MEMBER","cne":"R123456789","applicant_type":"STUDENT","applicant_first_name":"Rania","applicant_family_name":"Ben Ali","identifier_type":"MASSAR","promotion":null},"capabilities":{}}
```

The Delegate pending route returns those same nullable application values in each row, together with its existing `username`, account `first_name`, and account `family_name` fields.

The private applicant and Delegate responses are marked private/no-store by the backend. The application-options endpoint contains policy values only. No private values are placed in a URL, analytics, local storage, or console output.

## User-visible behavior

The request form requires an explicit applicant type and real application first/family names. It trims names, counts Unicode code points for the 100-character boundary, rejects blank/control/newline values, and leaves the account profile names unchanged. Student selection reveals the MASSAR/FOREIGN identifier choice and identifier input. MASSAR uses the one-ASCII-letter-plus-nine-ASCII-digits pattern and uppercases the letter; FOREIGN accepts 1–50 ASCII letters/digits and preserves case/leading zeros. Helper text makes clear that an entered identifier does not verify identity or document authenticity.

Laureate selection loads the authenticated options response. Presets are the response's completed-year values; a load failure or empty options response blocks a Laureate submission and offers retry. Custom promotion uses the response's supported format strings and checks ASCII `YYYY`, `YY`, `YYYY/YYYY`, or `YY/YY`, consecutive same-width year pairs, and the configured upper year. The backend remains authoritative and performs normalization.

The form disables duplicate submission and keeps values after field, server, or network errors. Successful submission calls the established AuthContext `refresh` and shows the updated membership status. Existing PENDING cancellation, REJECTED/REMOVED reapplication, ACTIVE status, BANNED denial, navigation, and authorization gates are preserved. A pending request displays: “Your request is usually reviewed within approximately 6 hours. If you have not received an update after that, contact Support.” Support links to `/support`; six hours is presented as an estimate.

Applicant details render only from the authenticated own-membership response. Null legacy details are displayed as unavailable; there is no inference from CNE, role, account name, or username. Delegate review shows account profile names and submitted names under separate labels. Student identifier values/type and Laureate promotion appear only in that authorized queue when supplied. Existing directory, staff, public, announcement, post, and discussion components were not extended with private application fields.

## Frontend handoff

Use the options endpoint's `promotion_options` for preset values and `custom_promotion_formats` for custom-input helper text. Submit exact fields `applicant_type`, `applicant_first_name`, `applicant_family_name`, `identifier_type`, `cne`, or `promotion` as applicable; never send both Student and Laureate-only fields. Read personal details only from the authenticated `/membership/me` response and Delegate details only from the target-community guarded `/membership/pending` response. Preserve nullable values as unavailable for legacy rows. Backend validation and normalization remain authoritative.
