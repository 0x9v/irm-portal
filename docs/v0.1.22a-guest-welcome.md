## Guest behavior

Before this change, a visitor without an account saw the general Home dashboard. It included module links despite the module list requiring authentication, a mixed membership/community guidance card, and guest-specific wording within dashboard panels. Home already avoided fetching announcements unless the visitor was an authenticated active member. It fetched modules for any signed-in account and cleared its protected content when there was no user. The initial authentication state was represented inside the dashboard rather than by a dedicated neutral Home state.

Now Home shows a neutral “Checking your account…” status while the initial `/auth/me` request is unresolved. A session-check error has its own neutral retry state and is not treated as a guest. Only after authentication resolves without a user does the page show the guest hero, prominent `/login` and `/register` links, concise module and community explanations, and `/support`. Guest Home does not issue module, document, announcement, or community data requests. Signed-in users continue through the existing Home tree, including the membership verification error treatment.

## Access decisions

- `GET /api/v1/communities/{community_slug}/modules` requires an authenticated user, so the guest page describes module resources and says they are available after sign-in instead of linking to the modules route.
- Global document routes also require authentication, so the guest page does not link to documents or claim they are public.
- `GET /api/v1/communities/{community_slug}/announcements` requires active community membership. Guest Home does not fetch or link to announcements.
- Community participation requires the appropriate signed-in membership access. The guest page describes this without linking to protected community actions.
- `/support` is a standalone frontend route and is linked directly.
